# アンドロイドが住み、働く条件を試す

名古屋駅周辺のCS1標準の住宅、職場、経路を使う。アンドロイドは試験用のCS1市民として空いた住宅ユニットに入り、CS1の標準AIが就職先を決める。MODは勤務時間と電池残量に応じて、その職場への移動と帰宅をCS1の標準移動処理に依頼する。充電速度と勤務時間は試験の仮定。

## 実ゲームでの結果

| 観測項目 | 結果 |
| --- | --- |
| 住宅への登録 | 3体。8体の導入設定に対して、その時点の空き住宅が3体分 |
| 職場ユニットへの所属 | 3体 |
| 自宅から自分の職場を目指すCS1標準の経路ID | 3体 |
| 職場に着いた市民IDの確認 | 1体 |
| 在宅中の充電開始 | 3体 |
| 人の職場割り当て数 | 導入直前23人、通勤確認時25人 |

同じセーブを進めながら取った前後の観測値。人の人数には時間経過や住民の出入りも影響する。導入による雇用への影響を測るには、導入なしの対照条件を同じ期間で繰り返す。駅周辺の観測で、市全域の求人や通勤を検証した段階ではない。

## 試験の実行条件

Androidの市民IDはこのゲーム実行中の試験用で、セーブを再読込した際のID管理は未実装。電池は在宅時に回復し、残量30%未満では定時出勤を見送る設定で、移動中の電池枯渇による停止や電力網の負荷はモデルに含めていない。

開始セーブは `NagoyaFlat-BeforeAndroidLife-20261119`。起動後、`H:/CS1-PLATEAU/nagoya-station/citywide-live-v1/android-life-state.json` の `runId` を使って、同じフォルダに `android-life-scenario.json` を作る。

```json
{"runId":"実ゲームのrunId","caseId":"station-android-life","androidResidents":8}
```

`androidResidents` は駅周辺版で0〜512。市民を追加できる数は住宅の空きによって決まる。MODは1回のゲーム実行で条件を1回読み込む。別条件では、旧シナリオファイルを退避してから開始セーブを開く。

## 全域版の店舗訪問と帰宅

全域建設用セーブは、市民IDと住宅ユニット、電池残量を保存する。店舗にいるアンドロイドについては、CS1で訪問中の建物を出発地にし、登録先の自宅までの移動をゲームに依頼する。帰宅は、ゲームの到着処理で同じ市民IDと自宅IDを確認できた場合に記録する。

電池は、歩行中の市民インスタンスから位置をサンプルし、計測した移動1メートルあたり0.025ポイント減る設定。車両での移動、経路待ち、停止中の時間は歩行距離に加えない。電力が供給されている住宅では、在宅中に電池残量が回復する。30%未満では新しい配送や定時出勤を見送り、帰宅は電池残量にかかわらず試みる。

守山区の試験では、アンドロイド `245513` が工場 `2839` から店舗 `19252` に商品100を運んだ。店舗を出て住宅 `37392` に到着し、電池残量が46.85%から91.85%に回復した。その後、同じ店舗への次の配送経路に入った。港区と緑区で配送履歴がある別の2体でも、店舗からの帰宅を確認し、残量は100%まで回復した。試験中は対象都市の資金制限を一時解除した。[在庫・到着・電池残量の実測](evidence/native-delivery-return-20261119.json)

## 同じセーブで増員の条件を比較する

全域建設用セーブを一時停止した状態で保存し、両条件で同じファイルを読み込む。試験中に保存すると、ランチャーの「再開」が別のファイルを指すことがあるため、元のセーブ名とハッシュを記録して照合する。

全域建設のデータフォルダの `native-employment-trial.json` に、対象都市 `city`、試験名 `caseId`、保存時の `expectedGameTime`、`expectedBuildIndex`、`expectedNetworkSegments`、`durationHours`、`additionalAndroids` を書く。読み込み時に建設状態を照合し、保存済みのフレームからゲーム内時刻を取得する。試験名には小文字の英字、数字、ハイフンを使用する。一度読み込んだ依頼は名前を変えて残す。

増員しない条件は `additionalAndroids: 0` にし、増員する条件と同じ時間を進める。終了するとゲームを一時停止し、`native-employment-<caseId>.json` に開始時・入居直後・終了時の記録を保存する。開始と終了のフレーム、フレームから求めた時刻、開始時の住民・職場が一致した結果は、`tools/compare_native_employment.py` で比較できる。

通常の資金制限の下で長めに比較する場合は、別名の `NagoyaCitywide-EmploymentTrial-*` セーブを作り、そのハッシュと保存時刻を `tools/stage_native_employment_trial.ps1` に渡す。最長30日間の比較で、開始資金は両条件に同じ額を一度だけ設定する。追加した開始資金は結果に別記し、税・交通収入と運営費はゲーム本体から読み取る。通勤・配送・充電の通常の処理も動かして比較する。

修復済みの全域セーブを使い、ゲーム内3月31日から4月4日まで、両条件を同じ2,341フレーム進めた。開始時の人は3,905人、アンドロイドは566体。256体を追加する設定に対して、住宅に入れたのは133体だった。

| 終了時 | 増員なし | 133体を増員 | 差 |
| --- | ---: | ---: | ---: |
| 人の入居 | 4,175人 | 3,930人 | −245人 |
| 人の職場登録 | 1,856人 | 1,839人 | −17人 |
| アンドロイドの入居 | 566体 | 699体 | +133体 |
| アンドロイドの職場登録 | 465体 | 480体 | +15体 |

追加した133体のうち8体に職場登録、6体に通勤経路、133体に充電開始を記録した。今回の観測で追加組の職場到着と店舗への配送は0件だった。資金制限は両条件で解除し、試験後に戻した。人の入居数も変わったため、職場登録の差だけでは、人とアンドロイドが同じ職を争ったかは判断できない。[同じセーブでの実測記録](evidence/native-employment-matched-20261119.json)

### 通常の資金制限での30日比較

全16区が稼働する同じセーブから、人9,066人、アンドロイド421体で始めた。開始残高は両条件ともゲーム内通貨200万に一度だけ設定し、継続的な資金補充を使わずに同じ17,555フレームを進めた。256体の追加要求に対し、空き住居があったのは123体分だった。

| 終了時 | 増員なし | 123体を増員 |
| --- | ---: | ---: |
| 人の入居 | 9,091 | 9,054 |
| 人の職場登録 | 4,184 | 4,151 |
| アンドロイドの入居 | 417 | 526 |
| アンドロイドの職場登録 | 404 | 511 |
| 店舗への配送完了 | 0 | 0 |
| ゲーム本体の内部残高 | 1,683,022.33 | 1,683,214.75 |

新規組では、終了時に職場登録が残っていた117体のうち116体で通勤経路、43体で到着処理の成功を記録した。充電開始は117体で観測した。両条件とも、全16区で人とアンドロイドの住宅・職場登録を確認した。人の入居数も変わったため、この1組の比較から人の職が置き換わったかは判断できない。店舗配送は出発していたが、経路を失った例や到着失敗があり、在庫更新まで完了した便はなかった。[同じ30日間の実測・条件・区別集計](evidence/native-employment-30-days-20261120.json)

### 工場から店舗への配送を再検証

同じセーブ・同じ増員123体・同じ17,555フレームで、配送の開始と終了の判定を再検証した。配送の予約は工場へ出勤した後に行うようにした。この変更と店舗訪問状態の検査を加えても、移動を見失ったと判定される便が残り、2回の再試験とも配送完了は0件だった。

経路の情報が見えなくなった場合に、最後に経路を確認したフレームから失敗までの時間を数えていた。最初に見失ったフレームから512フレームを計測し、経路が戻れば計測を解除するよう変更した。30日間の再試験では124便が出発し、全16区の52店舗に109便で計10,842を届けた。109便すべてで標準の到着処理と、工場の在庫減少・店舗の在庫増加を照合した。失敗は到着失敗8便と経路消失1便で、終了時点で6便が移動中だった。

緑区では、以前は経路消失と判定されていた `137034` が工場 `5743` から店舗 `18518` に到着し、工場の在庫が2,001から1,901へ、店の在庫が11,298から11,398へ変わった。標準の人口パネルでも配送109件を確認した。試験後の状態は `NagoyaCitywide-EmploymentTrial-Delivered109-30Days` として保存した。[比較条件・16区の内訳・全109便の在庫変化](evidence/native-delivery-route-grace-20261120.json)

## 既存の工場勤務者が新設店舗に届ける

新設店舗48棟を対象に15区で試し、空き住居への入居を伴わず、既存の工場勤務者6体に配送を割り当てた。勤務先、店舗の受け入れ枠と歩道経路はゲーム内の状態から確認した。

中区でアンドロイド `289237` が工場 `41265` から新設店舗 `22547` に商品100を運んだ。ゲーム本体の入荷要求に対応し、工場の在庫は4,736から4,636へ、店舗の在庫は12,844から12,944へ変わった。店舗から登録済みの住宅 `15805` に向かう経路を確認し、その後に同じ住宅で充電中の状態を観測した。電池残量は41.18%から86.18%に回復した。帰宅の到着コールバックはこの個体について記録されなかった。

約36日間の観測では、15区で計51便を工場と店舗の在庫で照合した。新設店舗を対象とした割り当てのうち、配送完了は中区の1便。試験の間だけ資金制限を解除した。最新セーブは `NagoyaCitywide-NewStoresExistingWorkers-Arrival`。[割り当て・入荷要求・在庫と充電の実測記録](evidence/native-new-store-existing-worker-20261119.json)
