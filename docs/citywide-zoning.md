# 名古屋全域の建物用途とCS1への接続

人とアンドロイドが同じ街で住宅、職場、店、道路、交通サービスを使い、導入条件を変えると就業や移動、店舗への配送がどう変わるかをCS1上で比較する。PLATEAUの建物IDを用途と街区に結び付けると、地域ごとの住宅や職場の条件を集計できる。

## 建物と用途地域

名古屋市の2022年度PLATEAUは376ファイル、738,178件の建物レコードを含む。実ゲームの描画カタログから書き出した738,033件の一意なIDを対象に、CityGMLの建物用途、用途地域の区画ポリゴンと国土数値情報の2022年行政区域を照合する。建物用途と行政が指定する用途地域は両方を保持する。用途地域の重複や未対応の地点は空欄として集計する。

## CS1の制約

導入済みのゲーム本体では建物枠は49,152件、道路セグメント枠は36,864件。既存セーブで開いている建設タイルは1枚で、実道路のうちゾーニング道路として確認した標準二車線道路は32区間だった。現在のセーブに原寸で全件を登録することはできない。

ゲーム側の建設範囲を25タイルまで広げる場合を想定し、元の接続を保つように道路の骨格を選び、元座標を約36%に縮めた道路計画を作成する。街区の住宅・商業・オフィス・工業は、同じ種類の複数のPLATEAU建物をCS1側の候補地に集約する。工場付き住宅などは用途別の候補を保持する。用途不明の建物に用途地域から仮用途を与えた場合は、明示的に記録する。

原寸の先行セーブで、開放済みタイルの標準二車線道路の近くにあるモデルは196件。道路と区画の正確な接続を確認した試験の [1棟の結果](plateau-zoning.md) は別に記録している。縮小案では道路1万6,000セグメント相当の骨格を選び、8,124件の街区・用途の組み合わせに対して2,228箇所の前面道路候補を作成した。

名古屋駅・広小路伏見・広小路栄・大須本町通・ささしまライブの停留所を、名古屋市交通局のGTFS-JPから選び、CS1に敷設済みの道路に合わせた。それぞれの候補道路に歩道2本があることを確認した。停留所はゲームの道路に合わせて配置した独自の循環ルートで、名古屋市の実在する系統とは停車順や経路が異なる。[名古屋市交通局のGTFS-JP](https://data.bodik.jp/dataset/231002_7109030000_bus-gtfs-jp)

最初に試した4停留所の案は大須から名古屋駅へ戻る経路が取れなかった。名古屋駅と大須の停車位置を変え、ささしまライブ経由にした後、全5区間の経路が成立した。通常資金のセーブで車庫からバス6台が出たことを読み戻した。路線開通の確認時点で乗客は0人で、車庫に電力の警告があった。[路線と車両の実測](evidence/native-central-bus-20261119.json)

破産警報が出たため、通常資金のセーブを保存し、乗車観測の間だけ資金制限を解除した。この観測ではバス12台が稼働し、広小路栄で停車した個体が次の大須本町通を目的地に保持していた。乗客の観測値は0人。各停留所の直線100m以内で稼働中の用途付き建物は1～6棟。画面ではPLATEAUの外観が車体に重なる箇所があった。

### 発電・下水・ごみ処理

発電所と南側の下水処理場は、CS1の判定が参照する入口と既存道路が施設の反対側にあった。施設ごとに2区間の道路を入口へつなぎ、どちらも「道路未接続」が消えた。道路網は市外高速道路まで1つにつながっている。

焼却場を南・中央・東・西の4か所に設置し、観測時は南・中央・東が稼働した。発電所のごみ警告は残った。送電線だけ延ばした段階では車庫が停止した。約65m離れた場所に風力発電所を設置して時間を進めると、車庫の電力警告が消え、車庫から経路付きのバス7台が出た。市全体に電力警告24件、電力網未接続391件が残り、路線の乗客は0人だった。

施設の稼働は一時的な資金制限解除のもとで観測した。修復後のセーブを分けて保存し、資金設定を戻した。[施設と運行の実測](evidence/native-service-grid-repair-20261119.json)

### 近隣の焼却場からの追加配車

`stage_native_finance_audit.ps1 -NearbyWasteDispatch` を試験用セーブで使用できる。ゲーム本体が出した収集依頼を使い、500 m以内に空き車両のある焼却場から追加で配車する。標準配車も動く。配車済みの建物は候補から外し、開始後96時間または12件に達した時点で追加配車を終了する。

ゲーム内で約10日観測し、3施設から12台が配車された。9台が経路を取得し、実際に走行して回収した。うち5台が指定先で計19,398単位を積み込み、2台の帰着時に積載を確認した。3台は経路探索に失敗した。検証用セーブでゲーム内融資20万を追加し、元のセーブを保管した。[車両と建物の照合記録](evidence/native-waste-nearby-dispatch-20261120.json)

同じ開始セーブから標準配車のみでも約10日進めた。両方とも開始時の市内のごみ警告1,278件は建物IDまで一致した。終了時は標準配車のみで1,269件、追加配車ありで1,260件だった。同じ64棟のうち実際に回収を観測した建物は、それぞれ4棟と13棟。対照側は14分15秒遅く始まり、22分40秒早く終わった。読み込み後に一部の建物のごみ量と残高もわずかに異なる。比較は1回なので、追加配車は試験用の設定として維持する。[標準配車との比較記録](evidence/native-waste-stock-control-20261120.json)

## 区画の登録と実際の稼働

ゲーム内で建て替えが始まった時点で、前面道路、ゾーンセル、用途、敷地寸法、位置と向きが一致する建物にPLATEAUとの対応を引き継ぐ。元より新しい建設番号を確認し、複数の候補が同じ建物を取り合う場合は引き継がない。

区画台帳に対応が残っている件数には、工事中や放棄された建物も含まれる。既存の `activeNativeZonedSites` はこの台帳上の件数。ゲーム本体が完成かつ稼働中と判定した区画は `operationalNativeZonedSites` に記録する。元のPLATEAU建物との対応を稼働棟に絞って確認するには、`audit_active_plateau_zoning.py --operational` を使う。

修正版で元のセーブを開くと、守山区と緑区で直前に対応が外れた3区画を含む計5区画が、建設中の住宅へ引き継がれた。`NagoyaCitywide-ConstructionRebinding-Verified` を開き直し、5件すべてが同じ建物IDに残っていることを確認した。台帳の7,260区画のうち、ゲーム本体で完成・稼働中は4,997棟、建設中5棟、放棄2,114棟、その他の非稼働144棟。この時点で全16区に人とアンドロイドの入居・職場登録があり、元のPLATEAU ID 574,439件は分類済みの全用途が稼働中の区画に対応していた。[建て替えとセーブ再読込の実測](evidence/native-construction-rebinding-20261120.json)

## 計測と再生成

Pythonのツールはデータと配置候補を書き出す。Python 3.12で実行し、用途地域と区の解析には NumPy、pyproj、Shapely 2.1以降を使う。道路と区画をロード済みの建設用セーブに反映するコマンドはPowerShellから実行する。
